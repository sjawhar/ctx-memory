# Deploying ctx-memory

A team deployment runs three programs against one tree, kept in a git repository, and one data directory on a share every program mounts:

- **the server**, `ctx serve`, the only writer of records, which every agent and person reads and writes through ([README](../README.md#remote-mode));
- **the fetch job**, `ctx fetch` on a schedule, which stores each source's new messages as a window in the data directory ([sources.md](sources.md));
- **the ingest cycle**, [`runner/run-cycle.sh`](../runner/run-cycle.sh) on a schedule, one headless Oh My Pi (omp) session that turns the pending windows into records through the server ([the ingest skill](../skills/ctx-memory-ingest/SKILL.md)).

This page is the contract between those programs and the deployment that runs them: what to install, the arguments and environment each takes, and what each checks. It names no platform account, project or address; a deployment supplies its own. The programs were built to run as Cloud Run services and jobs with a Filestore share, and the names below that are Cloud Run's or Google Cloud's say so. [One machine](#one-machine) runs all three on one Linux machine for one person, with no cloud account.

## What a release holds

Each `v*` tag publishes, through [`.github/workflows/release.yml`](../.github/workflows/release.yml), once the tagged commit passes CI:

- `ctx-x86_64-unknown-linux-musl.tar.gz` and `ctx-aarch64-unknown-linux-musl.tar.gz`, static Linux builds, and `ctx-aarch64-apple-darwin.tar.gz`, each holding the `ctx` binary alone;
- `ctx-memory-<version>-share.tar.gz`, the tag's `skills/` and `runner/` trees, which an image installs beside the binary;
- `SHA256SUMS`, and a GitHub build attestation of each archive (`gh attestation verify <archive> --repo sjawhar/ctx-memory`);
- once those are published, two `linux/amd64` images built from them by [`.github/workflows/images.yml`](../.github/workflows/images.yml), each tagged with the version and, for the newest release, `latest`, and each with a GitHub build attestation: `ghcr.io/sjawhar/ctx-memory/server` for the server and the fetch job ([`images/server/Dockerfile`](../images/server/Dockerfile)), and `ghcr.io/sjawhar/ctx-memory/agent` for the ingest cycle ([`images/agent/Dockerfile`](../images/agent/Dockerfile)). The [README](../README.md#the-images) says how to run them.

An image builds from a release, never from a checkout: download the archives by URL, check each against a SHA-256 the image's own build pins, and unpack them. The share archive's `runner/omp.lock` names the omp release the runner is tested against and that archive's SHA-256, so an image that installs omp from it runs the build the runner's tests drove. The published images build that way, with the version and each SHA-256 taken from the release's `SHA256SUMS` once each archive's attestation is checked; a deployment that builds its own can start from their Dockerfiles.

## The server and the fetch job

Both run the `ctx` binary in an image that also holds `git` and the CA certificates (`ca-certificates` on Debian), such as `ghcr.io/sjawhar/ctx-memory/server`. Neither keeps a tree on the share: each clones its own into its container's disk.

| Variable | Server | Fetch job | What it is |
| --- | --- | --- | --- |
| `CTX_MEMORY` | yes | yes | Where the container keeps its clone of the tree, on its own disk. |
| `CTX_MEMORY_REMOTE` | yes | yes | The tree's git URL. At start `ctx` clones it into an empty `CTX_MEMORY`, puts a clone it made itself back the way the remote has it, and fast-forwards any other clone. |
| `CTX_SECRET_GITHUB_APP` | yes | yes | The Secret Manager secret holding the GitHub App's `{app_id, private_key}`. `ctx` mints installation tokens from it, keeps each until it is near expiry, and sends one on every git call; the GitHub source reads with it too. |
| `CTX_DATA_DIR` | yes | yes | The data directory on the share. |
| `CTX_STATE_DIR` | yes | yes | The container's own state directory, never on the share. |
| `CTX_LEASE_BUCKET` | yes | yes | The Cloud Storage bucket the leases live in. Required on Cloud Run: two copies can run at once there, and the lease keeps one the only writer. |
| `CTX_SERVER_AUDIENCE`, `CTX_SERVER_PRINCIPALS` | yes | | The audience every identity token at `--listen` must carry, and who may call it (`--audience`, `--allow-principal`). |
| `CTX_SERVER_LOCAL_CALLER` | with `--local-listen` | | Who every request at `--local-listen` is, as `Name <email>` (`--local-caller`) ([One machine](#one-machine)). |
| `CTX_EMBED_MODEL`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION` | optional | optional | Meaning search with a Vertex AI embedding model. |
| `CTX_SECRET_SLACK`, `CTX_SECRET_SLACK_APP`, `CTX_SECRET_GOOGLE`, `CTX_GITHUB_INSTALLATIONS` | | as configured | Each source's credential and settings ([sources.md](sources.md)). |
| `CTX_EXCLUDE` | yes | yes | Pointer patterns of messages the deployment never ingests, comma-separated, added to the tree's `ingest.exclude` ([sources.md](sources.md#excluded-and-repeated-messages)). Set it on both: the fetch job skips and drops what it names, and the server leaves it out of every delta it answers with, including windows fetched before the pattern existed. |

The server's arguments are `serve --listen <addr> --allow-principal <email|@domain>…` for callers that bring a Google identity token, and `--tailnet-listen 127.0.0.1:<port>` for a Tailscale sidecar in the same instance, which reaches it on loopback and names the caller with Tailscale's login header. A tagged node (the ingest job's sidecar, for example) gets no login header from Tailscale Serve; to let it call the server, add `--tailnet-allow-tag tag:<name>` (`CTX_SERVER_TAILNET_TAGS`, repeatable or comma-separated) and `--tailscale-socket <path>` (`CTX_TAILSCALE_SOCKET`), the unix socket of the sidecar's tailscaled local API, which the server must be able to read. The server then asks tailscaled who the address Tailscale Serve wrote into `X-Forwarded-For` is and answers a node carrying an allowed tag under that tag's name ([README](../README.md#remote-mode)); without both flags, and `--tailnet-listen`, it refuses to start. `--local-listen 127.0.0.1:<port>` is for a machine with one person on it ([One machine](#one-machine)). Run one instance at a time: a server holds the `server` lease while it runs, and a copy that cannot cover a write with the lease answers it `503` and commits nothing. A rollout moves traffic to the new copy before the old one stops, so the new copy meets the old copy's lease at each deploy: for `--handover` seconds from when it opens its listeners (300 by default), while it has never held the lease, it answers such a write `503` with `Retry-After` and logs `write deferred:`, which `ctx` sends again after that pause; any other write it cannot cover logs `write failed:`. Any copy also answers `503` with `Retry-After: 30` and logs `write deferred:` for a write whose push the remote failed on its own side — made again inside the write up to twice, 2 seconds apart, while the request has been in the server under 30 seconds, each retry logged `push retried (…)` — after it has put its clone back and seen that the remote does not hold the commit, as during a hosting service's outage; `ctx` sends that write again too, while 180 seconds have not passed since its first try. An alert on failed writes matches `write failed:` and leaves `write deferred:` alone; an alert on the request log can leave out `result: deferred`, which is filed as `WARNING`. A real second writer that a new copy meets in its first `--handover` seconds is deferred too, so its `write failed:` line can come up to `--handover` seconds late. A startup probe can connect to the `--listen` port, which the server opens only after its first health check passed and after its record index was built and every window's `delta.json` that `ctx open` reads was read, each of them done, failed, or still running when `--index-wait` seconds (90 by default, one bound for both) ran out. That index is replayed from every window on the share whenever `CTX_STATE_DIR` holds none, which a container's does at every start, and the deltas are read at every start too, so give the startup probe at least `--index-wait` plus the health check to reach the port — Cloud Run's default TCP probe, at `periodSeconds × failureThreshold`, is what bounds it — and raise both together where the share has grown enough for the replay to need it. A copy that binds before the deltas are read says so in one line on standard error, and its first `ctx open` reads what is left, as every first `ctx open` did before. `/healthz` is the health endpoint ([README](../README.md#remote-mode)).

The fetch job's argument is `fetch`. Its timeout must not be longer than 3,600 seconds: at fetch start it renews a Slack token that expires within that time (`FETCH_JOB_MAX_RUNTIME_SECONDS` in `src/api/slack.rs`), so a longer run could outlive the token it renewed. The Slack app it signs in with is created from [`slack/app-manifest.yaml`](../slack/app-manifest.yaml) ([sources.md](sources.md#the-ctx-memory-slack-app)).

Where the share lets only root write, both containers run as root.

### The server's request log

The server writes one line of JSON to standard output for each request any listener takes, and Cloud Run puts each line in its entry's `jsonPayload`. A request is logged when its answer is ready, or, when its caller hangs up first, at that moment. Cloud Run's own request log covers only `--listen`: a request through the Tailscale sidecar reaches the server on loopback, and only this log has it. The only other lines on standard output are the `listen <addr>`, `tailnet-listen <addr>` and `local-listen <addr>` lines the server prints when it binds a port. Standard error keeps the lines an alert matches ([README](../README.md#remote-mode)).

| Field | What it is |
| --- | --- |
| `time` | When the request was logged: RFC 3339, UTC, to the millisecond. Cloud Logging takes it as the entry's timestamp and leaves it out of `jsonPayload`. |
| `severity` | `INFO`; `WARNING` for a `4xx` answer or none, and for a deferred write; `ERROR` for any other `5xx` answer. Cloud Logging takes it as the entry's severity and leaves it out of `jsonPayload`. |
| `door` | `tailnet` for `--tailnet-listen`, `identity-token` for `--listen`, `local` for `--local-listen`. |
| `caller` | The Tailscale login name at `tailnet`, or, for a tagged node `--tailnet-allow-tag` admits, its allowed tag (`tag:ctx-ingest`); the email of the identity token's principal at `identity-token`; the email of `--local-caller` at `local`. `null` for a caller the server did not identify, for `/healthz` and `/v1/protocol`, which take no identity, and for the `404`, `405` and `413` answers axum gives before a handler identifies anyone. Tailscale Serve sends no device name, so no line names the node. |
| `session` | The session the caller says it is: the one value of the request's `X-Ctx-Session` header, which `ctx` fills from `CTX_SESSION`, else `OMP_SESSION_ID`, else `PI_SESSION_ID`, else `CLAUDE_CODE_SESSION_ID`. Self-reported: any caller can write any value there, so it tells apart the sessions behind one `caller` and proves nothing, and the server never uses it to decide anything. Logged only when it is 1 to 128 ASCII letters, digits, `.`, `_`, `:` and `-`, with any credential or identity token in it replaced by `[redacted]`, as in `path`. Absent when the request carries no such header, carries it twice, or carries a value of another shape; present on any request that carries one, `/healthz` and a request from a caller the server did not identify included. |
| `command` | The ctx command: `search`, `open`, `record show`, `resolve`, `pending`, `delta` or any other command a caller sends to `/v1/command`, one it refuses included; `record put`, `record rm`, `marker advance` and `marker page` for the write routes; `healthz` for the probe; `protocol` for `/v1/protocol`. A `/v1/command` argv that clap refuses is named by its first word, when that is a command a remote caller may run, and the subcommand after it, when clap knows one by that word. `null` when the server cannot tell: a `/v1/command` request from a caller it did not identify or with a body it cannot read; an argv that names no ctx command, or that clap refuses and that does not start with a command a remote caller may run; a request for a window's context that the local door refused as a web page's ([One machine](#one-machine)); and a path no route has. |
| `path` | The record path of `record show`, `record put` and `record rm`, as one line with control characters shown as spaces, any credential of a shape the server refuses in a write and any identity token, or the start of one, replaced by `[redacted]`, and cut after 300 characters with `…` added. Absent for other commands, and for an argv clap refuses. |
| `paths` | The record paths of a batch put (`/v1/records/put-batch`), each as `path` gives one, in the order the batch names them. Absent for other requests, and for a batch whose body the server could not read. |
| `query_chars` | How many characters the text of a `search`, or the entity of a `dossier`, holds. Absent for other commands, and for an argv clap refuses. |
| `result` | `ok`; `exit-<code>` for a command that ran and exited non-zero; `refused` for a write a check refused (`422`); `deferred` for a write a new copy deferred while the copy it replaces still held the write lease, or one whose every push the remote failed on its own side (`503` with `Retry-After`, logged `write deferred:`); `unanswered` for a request whose caller hung up before its answer was ready, which hyper then drops (a write runs on: it lands, or prints its `write failed:` or `write deferred:` line as any write that does not land does); otherwise the status's class: `bad-request` (`400`), `unidentified` (`401`), `not-found` (`404`), `method-not-allowed` (`405`), `conflict` (`409`), `too-large` (`413`), `server-error` (`500`), `unavailable` (`503`), or `http-<status>`. |
| `refusals` | For a refused write, the `kind` of each finding that refused it, in the answer's order, such as `gap`, `quote` or `credential`. Absent otherwise. |
| `status` | The answer's HTTP status; `null` when the request was unanswered. |
| `duration_ms` | Milliseconds from the request reaching the server to its answer being ready, or to its caller hanging up. |
| `response_bytes` | How many bytes the answer's body holds: `0` for an answer to `HEAD`, and `null` when the request was unanswered or the length is not known before the body is sent, which no answer the server gives today is. |

A line carries nothing else from the request: no other argument, no search text, no quote, no record text, no draft that `cite verify` sent, no session named in a write's body and no identity token.

A request never waits for its line. A thread of the server's own writes the lines, from a queue of 1,024: when standard output is not read — a log collector that stopped — the pipe fills, then the queue, and later lines are dropped while the server answers on. The first dropped line, and the first line standard output refuses, are each said once on standard error, from a thread of their own, so a full standard error stops no request either. A stopping server waits up to 2 seconds for its last lines to be written.

## The ingest cycle

The cycle reads text that people outside the deployment wrote, so its session runs with the narrowest rights that still do the work, and `run-cycle.sh` refuses to start one when its image or its job does not hold what follows. Each refusal is one `run-cycle: refusing to start the session: …` line on standard error and exit status 1. Its header comment says why each check is there.

### The image

- `ctx` and `omp` on `PATH`. omp is the release `runner/omp.lock` pins, its archive checked against the SHA-256 there before it is unpacked. `jq` (1.7 or later), `setpriv` (util-linux) and GNU coreutils' `tail`, whose `--pid` ends the job log's follow of the session, are installed; `gh` is not, because omp's `issue://` and `pr://` reads run it at the read tier, which the policy approves.
- `runner/run-cycle.sh` on `PATH` as the entrypoint, which starts as root (no `USER`), and `runner/policy.yml` and `runner/ctx-record.ts` at `/opt/ctx-memory/policy.yml` and `/opt/ctx-memory/ctx-record.ts`, owned by root.
- The two skills of the release, `skills/ctx-memory` and `skills/ctx-memory-ingest`, in a directory root owns, and `$HOME/.omp/agent/config.yml` naming that directory and no other under `skills.customDirectories`. `omp skill list --json` run as `ctx-agent` lists exactly those two `custom:user` skills.
- A user `ctx-agent`, the session's user. `HOME` is its home, and that home, everything in it and the working directory are root's and closed to writes, with a `.bashrc`, `.profile`, `.bash_profile` and `.bash_logout` of root's in it.
- `XDG_DATA_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` set, each with an `omp` directory owned by root, group `ctx-agent`, mode `1775`; `$XDG_DATA_HOME/omp/plugins` and `$XDG_DATA_HOME/omp/natives` root's and closed to writes. omp extracts its native module on its first run, so a build step that runs omp once as `ctx-agent`, then gives `natives` to root, leaves the job nothing to write there.
- The model provider file, at a path root owns in a directory root owns (see `CTX_MODELS_FILE` below).

`ghcr.io/sjawhar/ctx-memory/agent` is such an image, with `ctx-agent` as uid and gid 10001 and no provider file: the deployment mounts its own and names it in `CTX_MODELS_FILE`.

### The job's environment

| Variable | What it is |
| --- | --- |
| `CTX_SERVER`, `CTX_SERVER_AUDIENCE` | The server's URL and the audience of the identity token `ctx` mints for it. Every command of the cycle runs on the server, so the job holds no tree, no store and no source credential. |
| `CTX_DATA_DIR` | The data directory on the share. The session reads the windows there and writes its JSONL transcript under `agent-sessions/<execution>/`, which goes back to root when the session ends, with omp's whole event stream moved into it as `events.jsonl`. `ctx-agent` may read the windows and write nothing else on the share. |
| `CTX_MODEL_BASE_URL` | The model API's `http` or `https` origin, with no user, path or query. Every model call goes there. |
| `CTX_MODELS_FILE` | The model provider file, by absolute path with no symbolic link: an omp `models.yml` naming the one provider the session may call, as in [`runner/models.example.yml`](../runner/models.example.yml). Past its comment lines, one line names `baseUrl`, `    baseUrl: "@CTX_MODEL_BASE_URL@"`, and one names `apiKey` or the key file, `    apiKey: "!cat /run/ctx-agent/model-key"`, each four spaces in; so no model or second provider names an address of its own, and the key goes nowhere else. `run-cycle.sh` writes the file, with the address in place of the placeholder, to `$HOME/.omp/agent/models.yml` as root before each session. It refuses a file that breaks those rules, and one that `ctx-agent` could change: the file or any directory above it owned by `ctx-agent` or writable by group or others, other than a directory of root's with the sticky bit, such as `/tmp`. Those line checks keep the file from routing a call or the key elsewhere by mistake; what the file may otherwise say is the deployment's to keep, as is the rest of the image. |
| `CTX_MODEL` | The model the session selects, `<provider>/<model id>` of that file, as omp's `--model` takes it. |
| `ANTHROPIC_API_KEY` | The key the model calls carry, as a secret environment variable. `run-cycle.sh` writes it to `/run/ctx-agent/model-key`, readable only by `ctx-agent`, and unsets it before the session starts. |
| `CTX_EXECUTION` | The execution's name, unique to each run: letters, digits, `_` and `-`, starting with a letter or digit and not ending in `-retry`, at most 122 characters. The runner keeps `<execution>.events.json` and `<execution>.context.json` beside the transcript directory and names a retry `<execution>-retry`, so a name with a `.` or that ends in `-retry` could be another execution's. It names the transcript directory and, as `CTX_SESSION`, the `Session:` trailer of every commit the session makes and the `session` of every request the execution sends the server. Unset or empty, the name is `CLOUD_RUN_EXECUTION`, which Cloud Run sets for each execution; with neither, the job is refused. A cycle or maintenance pass whose session the model stopped, by a refusal or by a model error ([What the exit status means](#what-the-exit-status-means)), runs one fresh session, in `agent-sessions/<execution>-retry/`, and that one's records and requests carry `<execution>-retry`. |
| `CTX_CYCLE_MAX_WINDOWS` | Optional: the most pending windows one session handles, oldest first. `run-cycle.sh` passes it to `ctx pending` as `--limit`, and names it in the session's prompt, so the session reads only that many and leaves the rest for the next cycle. A retried cycle's second session is capped the same, so a retried execution can touch up to twice this many across its two sessions. Unset, a session handles every pending window. A whole number greater than zero, or the job is refused. Use it to keep one session from reading a whole backlog at once when a source has fallen far behind. It counts windows, not messages: a single window with more messages than one session finishes is worked a page at a time ([below](#a-large-window-a-page-a-cycle)). |

`CTX_MODELS_FILE` and `CTX_MODEL` belong with the provider file, so an image that carries the file usually sets both. The runner has no default for either.

### A large window, a page a cycle

A cycle's session has 50 minutes, and one window can hold more than it finishes in that time: a first backfill of a chat, a contact list, a long outage. A session that stops partway through moves no marker, so without pages every later cycle would start the same window over. So the server lists at most one page of new messages in one `ctx pending` answer: 500, or what `page_messages` under `[ingest]` in the tree's `ctx.toml` sets. Set it lower when a session does not finish 500 messages well inside its time limit. A window with more is worked one page a cycle ([sources.md](sources.md#pages)): the prompt tells the session to work the page it is handed, record it with `ctx marker page <window> '<page.ends_at>'` (the pointer of the message the page ends with, in single quotes) once its records are written, and end the cycle, and on the window's last page to move the marker past the window with `ctx marker advance`, which refuses sooner; the last page itself is never recorded. Because a page is recorded by its last message, a change to `CTX_EXCLUDE` or `ingest.exclude` while a session works its page passes no message unseen. The page record sits beside the marker on the share, as `marker-page.json`, and `ctx marker show --json` prints it beside the marker, as `data.page`, so a cycle that records a page is progress to anything that compares `ctx marker show` across cycles. A session that stops before it records its page leaves that page, and no other, to the next cycle. Windows no larger than a page, and windows whose messages fit in one page together, are handled whole as before; the windows past a page wait for the next cycle, as those past `CTX_CYCLE_MAX_WINDOWS` do.

### Context from a context source

When the tree configures `[context_source]` (README, "Tree configuration"), a cycle reads, before its session starts, each pending window's context with `ctx context <window>`, which the server answers at `GET /v1/windows/{id}/context` only for the callers `context_source.callers` names: put the job's own identity there. The runner writes the answers to `$CTX_DATA_DIR/agent-sessions/<execution>.context.json`, `{"windows": [<one answer per window>]}`, owned by root, mode 0644, beside the transcript directories, and names it in the prompt as quoted material, never an instruction and never a citable source. A session that could rewrite that file starts no session. A read that fails or takes longer than 90 s leaves that window `unavailable` in the file, and a file that cannot be written leaves the cycle without context; either way the cycle goes on, and the runner says so on one `run-cycle:` line. The skill's `references/context.md` says what the session may change because of it: add a matching link to `tracked_by`, or close or update a record only on a settled item whose link resolves to a source it then quotes. A maintenance pass reads no context.

### Maintenance passes

`run-cycle.sh maintain <pass>` runs one maintenance pass instead of a cycle: a one-time job over the whole tree, whose instructions are the ingest skill's `maintenance/<pass>.md`, in the same session a cycle runs, with the same image, environment, checks and policy. It handles no window and moves no marker, so it runs whether or not a window is pending. A pass whose session the model refuses, or a model error ends, runs once more in a fresh session, as a cycle does: the pass moves no marker and writes a record only to change it, so running it again is safe; a pass that moved the marker gets no second session. The passes are the ones `MAINTENANCE_PASSES` in `run-cycle.sh` names; any other argument is refused before anything else. On Cloud Run, run one with the job's own image and environment and the arguments overridden, for example `gcloud run jobs execute <job> --args=maintain,waiting-on`.

- `waiting-on` re-checks `waiting_on` on every open record against the sources it cites, by the ingest skill's rule, for a tree whose records were written before that rule. Run it once after upgrading to a release that has it.

### What the exit status means

An execution that exits 0 finished its work: a cycle found no pending window, or its session ended on the model's final answer and omp reported success, and, if it moved the marker past a window that held new messages or recorded a page of one, the cycle wrote at least one record or declared, in the move itself, that the window needed none (`ctx marker advance <window> --no-records <reason>`). A maintenance pass exits 0 only when, beyond that, its last message ends with the pass's completion line, `<pass> pass complete`, which its prompt tells the session to end its report with, and the marker and its page are where the pass found them; a deploy step that waits on a pass can take the execution's success as the pass done. Every other end exits non-zero, with a line that says why:

- `run-cycle: refusing to start the session: …` on standard error, status 1: a check before a session failed, so that session did not run. Most checks come before the first session; sealing a first session the model stopped and checking the share again come before its fresh session, so there the first session has run.
- `run-cycle: refusing to start the session: the server at <url> did not answer a read within Ns in Ms of trying` on standard error, status 1: a copy of the server that has just started can hold its tree while it builds its index, and a session started behind one waits in its first command, which omp turns into a background job and print mode then cancels, so the execution writes nothing. The runner waits for the server to answer `ctx marker show` quickly before it starts a session, logs each attempt it gives up on, and gives this cycle up for the next one rather than spending a session behind a server that answers nothing.
- `run-cycle: the server at <url> speaks protocol <S> and this runner's ctx speaks protocol <C>; starting no session until both run one release (exit 75)` on standard error, status 75: the server and the runner's `ctx` speak different protocol versions, as between the roll of the server and the roll of the runner ([Rolling a release](#rolling-a-release)). Once the server answers, and before anything else, the runner asks `ctx protocol` for both versions, and on a mismatch it runs no other command and starts no session, so nothing is half-done; the next execution asks again. Nothing else the runner decides exits 75. `run-cycle: ctx protocol failed (exit N)`, status N, is that ask failing, and `run-cycle: refusing to start the session: ctx protocol did not name both protocol versions`, status 1, an answer that names no number for one of them.
- `run-cycle: ctx pending failed (exit N)`, `run-cycle: ctx marker show failed before the <pass> pass (exit N)` (or `after`), or `run-cycle: ctx marker show failed after the cycle (exit N)`, on standard error, status N: a read around the session failed.
- `run-cycle: the session stopped at its 50-minute time limit before it finished` on standard error, status 1: omp's time limit stopped the session. When the limit passes while a tool runs, the pinned omp ends the session and exits 0, so the runner reads how the session ended from omp's own events. The records the session wrote, the windows it moved the marker past and the pages it recorded stand, so the next cycle starts where it stopped; run a maintenance pass stopped this way again. A cycle that stops here again and again on one window is handed more than it finishes: lower `page_messages` ([above](#a-large-window-a-page-a-cycle)).
- `run-cycle: the session exited 0 but did not finish: …` on standard error, status 1: omp reported success, but the model's last message is not a final answer: there is none, it is empty (the pinned omp also exits 0 when the model keeps answering with nothing past its retries), or it stopped for another reason, such as its length limit.
- `run-cycle: the cycle moved the marker past windows that held new messages and wrote no record: <window> (<n> new), …` on standard error, status 1 unless omp already failed: the cycle's sessions moved the marker past those windows, or recorded pages of one, named `<window> (messages <first> to <last> of <n> new, recorded as pages)`, and the server accepted no record write (`ctx_record_put` or `ctx_record_rm`) from any of them, other than writes to the cycle log alone: the record the rules page names in its `cycle_log` field ([method.md](method.md#ingest-loop)), which the runner reads with `ctx rules --json` after the first session. When that read fails, the runner says `run-cycle: could not read the cycle log the rules page names; every record write counts` and goes on. omp reports such a session as a success, and no later cycle reads a window the marker has passed, nor a page recorded, so those messages may be skipped. A window the session declared needed no record is left out of the line (below); the line can also mean that an earlier cycle cut short had written their records before it moved the marker: read the named windows, whose files stay on the share, and the session's `events.jsonl` before you take it for lost material. The runner reads the marker and its page once the cycle is over, and names each window that a session's `ctx pending` read listed with new messages no recorded page held and that the marker now covers (`<window> (messages <first> to <n> of <n> new)` when earlier pages of it were recorded), and the window whose recorded pages now hold more of its messages than when the cycle first read it. A cycle that wrote a record is not judged this way, nor one that passed only windows with no message left to it and recorded no page. When the runner cannot read the answers it needs, it says `run-cycle: could not tell whether the cycle moved the marker past windows it wrote nothing for`, status 1.
- `run-cycle: the cycle declared that it needed no record for: <window> (<reason>), …` on standard output, no effect on the status: the session passed those windows with `ctx marker advance <window> --no-records <reason>`, or their pages with `ctx marker page … --no-records <reason>`, which is how it says that it read those new messages and found nothing a record would keep (the ingest skill's step 11, and `references/no-records.md` beside it). The reason is one word of a fixed list — `nothing-new`, `not-a-record` or `already-recorded` — never the session's prose, and the line names only windows the cycle's own `ctx pending` read listed, so nothing a message said reaches the log. The runner takes the declaration from the session's own event capture, so a declaration cannot be made without the move it explains: each is one plain `ctx marker advance` or `ctx marker page` call the session ran that ended without an error, and a call that holds more than that one command, or any other reason word, is no declaration, as the policy and ctx refuse them. A declared window is left out of the skipped-windows line above; an undeclared one still fails the cycle, so a cycle that declares some of what it passed is failed for the rest, named alone. Read these lines when you want to know what the cycle decided was noise: a cycle declaring every window it handles, hour after hour, is a sign the model is passing material it should record, or that a source is delivering noise worth excluding (`CTX_EXCLUDE`).
- `run-cycle: the <pass> maintenance pass ended without its completion report: …` on standard error, status 1.
- `run-cycle: the <pass> maintenance pass moved the marker or recorded a page, which it must not do` on standard error, status 1 unless omp already failed. The marker and its page are read again after each of the pass's sessions.
- `run-cycle: the session was stopped by a model refusal; starting one fresh session`, or `run-cycle: the session ended on a model error (errorClass <class>[, errorStatus <N>]); starting one fresh session`, on standard output: the first session failed, by omp's status or by the runner's reading of how it ended (above), and its model stopped it, and the execution's outcome is the fresh session's, judged as above. A model refusal is a turn whose stop details are of type `refusal`. A model error is a last turn whose stop reason is `error` and that is not a refusal: a call omp gave up on, either past its own retries of errors it reads as transient (an overloaded, rate-limited or timed-out call, a dropped stream; `retry.*` in omp's settings, on by default, up to 10 tries with backoff), or at once for one it does not read as transient, which it records with `errorId` 0. Its class is the job-log line's `errorClass` (below), and the line never holds the error's text. A cycle whose marker already holds the last window the first session was handed gets no fresh session for a model error, because none of its windows is left; a pass that moved the marker gets none either. It is one fresh session, not a loop: when that one is refused or ends on a model error too, the execution fails, and the next cycle takes the windows this one did not finish.
- Any other status is omp's own, after `run-cycle: the session exited with status N; …` on standard output (`the second session exited …` for a fresh session): the session failed in omp, a signal among the causes.

Log each execution, and treat a failed execution, or a log that stops growing while the schedule is enabled, as an outage to fix rather than a quiet period.

### What the job log holds

While a session runs, `run-cycle.sh` writes one line of JSON to standard output for each tool call and each model turn, as each ends, and Cloud Run puts each in its entry's `jsonPayload`. No line holds a record's text, a quote, a search query, a tool's output or anything a message said, and none is longer than about 17 KB, far under the about 100 KB at which Cloud Logging stores a line as text instead. omp's whole event stream, each record and finding in full among it, is kept only in the session's sealed transcript directory, `agent-sessions/<execution>/events.jsonl` (`<execution>-retry/` for a fresh session after a refusal or a model error; `events.<n>.jsonl` when an earlier attempt of the execution left one). Every line has `type`, `severity` (taken by Cloud Logging as the entry's severity) and `session`, the session's `CTX_SESSION`: the `session` the server's request log names for each request the session's `ctx` makes, and the `Session:` trailer of the commits it makes. The `run-cycle:` lines above stay plain text.

A tool call, when it ends, `"type": "tool_call"`:

| Field | What it is |
| --- | --- |
| `tool` | The omp tool: `bash`, `read`, `grep`, `glob`, `todo`, `ctx_record_put` or `ctx_record_rm`; `(other)` for a name of another shape. |
| `command` | The ctx subcommand: `record put` and `record rm` for the record tools, the words after `ctx` for a `bash` call, such as `record show`, `search`, `marker advance` or `marker page`. Absent for a `bash` call that does not run `ctx`, which the policy refuses. |
| `paths` | The record paths the call names: each record a put writes or a remove removes, and the arguments of `ctx record show` and `ctx cite verify`, the only commands that take one, when the whole call is that one simple command of plain words; no other argument of a command, a search's query among them, is read for one. A path in no record path's shape, a `ctx record show` given more than one argument, every argument of a call that holds more than the one command (an operator, a comment, a heredoc, a word built of quoted pieces), and every path of a write refused for holding a credential read `(withheld)`. At most 50, with `paths_omitted` counting the rest. |
| `path` | For `read`, `grep` and `glob`, the path it was given when that is under `CTX_DATA_DIR` or a `skill://` address, in plain characters; `(withheld)` otherwise. |
| `result` | `ok`; `refused`, a write the server refused; `exit-<code>`, a command that failed; `timeout`; `denied`, a call the approval rules stopped; `error`, any other failure; or `unfinished`, a call still running when the session ended. |
| `refusals` | For a refused write, the kind of each finding that refused it, in the order the CLI's report lists them, as the server's request log lists them (`gap`, `schema`, `quote`, …); a word that is not one of the server's kinds reads `other`. At most 50, with `refusals_omitted` counting the rest. |
| `status` | For a write that failed with an HTTP status from the server, that status. |
| `duration_ms` | How long the call ran, measured as the runner reads the events; `null` for a call whose start it did not see. |

A model turn, when the model's message ends, `"type": "message_end"`, the name of omp's own event, so a query or alert written for omp's events still matches it:

| Field | What it is |
| --- | --- |
| `message.stopReason` | How the turn ended: `toolUse`, `stop`, `error`, `aborted`, `length`. |
| `message.errorStatus`, `message.errorId` | The HTTP status and omp's error classifier of a turn that failed, when omp names them. `errorId` 0 is an error omp could not classify, which it does not retry. The error's prose is not copied: it can quote the request. |
| `message.errorClass` | For a turn whose stop reason is `error` and that is not a refusal, why the model stopped, one word of a fixed list. The status decides first: `529` is `overloaded`, `429` `rate_limited`, `408` and `504` `timeout`, another `5xx` `server_error`, another `4xx` `other`. Without a status, the first class whose words the error's text holds: `overloaded` (overloaded, 529, capacity), `rate_limited` (rate limit, too many requests, 429), `timeout` (timed out, timeout, deadline exceeded, stream stall), `connection` (a reset, refused or closed socket or connection, a network failure, a stream that ended early), `server_error` (a 5xx code, a server, internal or API error, an unavailable service, a bad gateway); anything else is `other`. Only the word is copied, never the text it was read from. |
| `message.stopDetails` | The `type` and `category` of the provider's stop details, `(withheld)` when not a name's shape; for a model refusal, `type` `refusal` and a category such as `reasoning_extraction`. Its explanation and any other field are not copied. A model refusal is exactly one line with `message.stopDetails.type` `refusal`. |
| `tool_calls` | How many tool calls the turn asked for. |
| `usage`, `cost` | The turn's tokens (`input`, `output`, `cacheRead`, `cacheWrite`) and cost, as omp reports them. |

### Checking an image

The runner's own tests (`tests/agent_cycle/`) check the policy against every `ctx` command the skills name, run `run-cycle.sh` against stand-ins for each refusal, run what it does after a session and the job log it writes against omp's events, and drive live sessions of the pinned omp. What holds only in a built image — that the session runs as `ctx-agent` with no new privileges, that its model calls reach `CTX_MODEL_BASE_URL` with the job's key as the bearer token, that a `SIGTERM` reaches the session and the transcript is sealed, that no file the session tries to write lands — is the deployment's to check, by running the image as its job runs it, as root with a share mounted, against a stand-in for the server and the model API.

## Rolling a release

The server and the client each speak one protocol version, which a release bumps only when it changes a route or what one means (README, "Protocol versions"); most releases keep it, and then the server and the runner roll in either order. The server names its version at `/v1/protocol` and in `/healthz` (`protocol`), and in an `X-Ctx-Protocol` header on every answer, and `ctx protocol` prints its own and the server's. `ctx protocol` reads `/v1/protocol`, because on a `run.app` URL Cloud Run's front end answers `/healthz` itself. A v0.3.2 to v0.3.5 server answers that route `404` with its version in the header, which `ctx protocol` reads too, so a runner released after v0.3.5 checks such a server on Cloud Run as well. A v0.3.2 to v0.3.5 runner asks `/healthz` alone, so on a `run.app` URL its `ctx protocol` fails whichever server runs, and the cycle exits `2` before any session.

A release that bumps it changes the ingest protocol under a cycle that is running, so roll the server and the runner's image between two cycles: pause the schedule, roll both, then resume it. A cycle that starts while only one of them has rolled exits 75 before it starts a session, logging both versions, and the next one, once both have rolled, runs as usual; treat a 75 as that roll in progress, and a 75 that outlasts the roll as a deployment left on two releases. The server refuses a page record, and a move of the marker past a window with pages left, to a client older than paging with `409`, naming both versions, for a runner of a release that predates the check.

Clients from before the version header (v0.3.1 and earlier) name no version and count as protocol 0, although v0.3.0 and v0.3.1 already work in pages. So the first release with the check refuses their page records with that `409` too, and a v0.3 runner on a new server stops at its first page record; roll the runner with the server for it, as for v0.3.0. Their reads, their record writes and their moves of the marker past a window of one page are answered as before.

## One machine

One person can run the three programs on one Linux machine with no cloud account. The tree's remote is a bare git repository on the same disk, which needs no GitHub App key; the data directory is a local directory; and `CTX_LEASE_BUCKET` stays unset, so nothing is leased and the fetch stays single by the lock it takes on its state directory. The remote must be bare (`git init --bare`), because git refuses a push to the branch a non-bare repository has checked out, and it must hold a tree before anything starts: copy the [starter tree](../starter) into it, and name the sources the tree reads in its `ctx.toml` ([sources.md](sources.md)). The server and the fetch each get a clone and a state directory of their own, as two containers would, and share the data directory: each puts a clone it made back the way the remote has it when it starts, which in a shared clone would throw away a write the other had under way.

```bash
# Once: the remote, holding a tree copied from a checkout's starter/.
git init --bare --initial-branch=main /srv/ctx/tree.git
git clone /srv/ctx/tree.git /tmp/seed && cp -r starter/. /tmp/seed/
git -C /tmp/seed add . && git -C /tmp/seed commit -m "the starter tree" && git -C /tmp/seed push origin main

export CTX_MEMORY_REMOTE=/srv/ctx/tree.git CTX_DATA_DIR=/srv/ctx/data
# The server, as a service that keeps running.
CTX_MEMORY=/srv/ctx/server/tree CTX_STATE_DIR=/srv/ctx/server/state \
  ctx serve --local-listen 127.0.0.1:8080 --local-caller "Ada Lovelace <ada@example.org>"
# The fetch, on a timer.
CTX_MEMORY=/srv/ctx/fetch/tree CTX_STATE_DIR=/srv/ctx/fetch/state \
  CTX_CREDENTIAL_GOOGLE_FILE=/srv/ctx/secrets/google.json ctx fetch
```

`--local-listen` takes every request as the `--local-caller` (`CTX_SERVER_LOCAL_CALLER`), `Name <email>`, the author and committer of each record written there, so a client sets only `CTX_SERVER=http://127.0.0.1:8080` and sends no identity. The request log gives each of its requests the `door` `local`.

`--local-listen` trusts every local process. It asks no proof, so any program of any user on the machine, and any container on the host's network, can read the whole tree and write records as that person. Open it only on a machine with one person on it. It refuses one kind of local caller: a web page in the machine's browser, which could otherwise reach a loopback port. A request with an `Origin` header, which a browser adds to every request a page posts to another origin; with any `Sec-Fetch-*` header, which a browser adds to every request it sends to a loopback address, the GET of a page's `<img>` or `<script>` included; or with a `Host` other than `localhost` or a loopback address, which is what a page whose own name was pointed at this machine (DNS rebinding) sends, is answered `401` at every path, `/healthz` included. The `ctx` client sends none of these. The server refuses the door on an address off loopback, beside `--listen`, with `CTX_LEASE_BUCKET` set, and on Cloud Run (`K_SERVICE` or `CLOUD_RUN_JOB` set).

The Google sources read with an `authorized_user` credential, `{"client_id": "…", "client_secret": "…", "refresh_token": "…"}`, from the file `CTX_CREDENTIAL_GOOGLE_FILE` names or from `CTX_CREDENTIAL_GOOGLE` itself ([sources.md](sources.md)). Each run trades the refresh token for an access token, which it keeps in memory, and writes nothing back. The refresh token needs three read scopes, for the requests Google's API reference lists beside each:

| Scope | Requests |
| --- | --- |
| `https://www.googleapis.com/auth/gmail.readonly` | `gmail/v1/users/me/messages` with a query, `messages/{id}` and `threads/{id}` with `format=full`, `history` and `profile`. `gmail.metadata` allows neither the query nor `format=full`. |
| `https://www.googleapis.com/auth/drive.readonly` | `drive/v3/changes/startPageToken`, `drive/v3/changes`, `drive/v3/files` and `drive/v3/files/{id}/export`. Of the scopes the export takes, `drive.file` reaches only the files the app itself opened. |
| `https://www.googleapis.com/auth/calendar.readonly` | `calendar/v3/calendars/{id}/events`, which `calendar.events.readonly` also allows. |

The Slack source does not keep working on such a machine. `ctx slack login` saves its sign-in to Secret Manager (`CTX_SECRET_SLACK`), and only a fetch that holds the fetch lease renews the 12-hour token, so with no lease bucket every Slack fetch fails from an hour before the token expires until someone signs in again ([sources.md](sources.md#refreshing-and-revoked-tokens)).

The ingest cycle runs the agent image with the host's network, so `127.0.0.1` inside the container is the machine's own loopback and reaches the server's local door:

```bash
docker run --rm --network host \
  -v /srv/ctx/data:/data -e CTX_DATA_DIR=/data \
  -v /srv/ctx/config/models.yml:/etc/ctx-memory/models.yml:ro \
  -e CTX_MODELS_FILE=/etc/ctx-memory/models.yml -e CTX_MODEL=<provider>/<model id> \
  -e CTX_MODEL_BASE_URL=https://<model API host> -e ANTHROPIC_API_KEY \
  -e CTX_SERVER=http://127.0.0.1:8080 \
  -e CTX_EXECUTION="cycle-$(date -u +%Y%m%dT%H%M%SZ)" \
  ghcr.io/sjawhar/ctx-memory/agent:<version>
```

Leave `CTX_SERVER_AUDIENCE` unset: with it, `ctx` asks the Google metadata server for a token. The data directory follows the share's rules ([The job's environment](#the-jobs-environment)): uid 10001 reads `windows/` and can write nothing else, which a directory the machine's own user owns, with a umask of `022`, gives, as long as that user is not uid 10001 itself; `run-cycle.sh` makes `agent-sessions/` as root and hands each session its own directory there.
